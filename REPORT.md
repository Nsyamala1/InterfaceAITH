# Design Report

## 1. Architecture

A single Node/TypeScript workspace, two packages: `packages/agent` (the automation system) and `packages/mock-bank` (the target surface — a local, legacy-style server-rendered banking app, standing in for a real back-office tool). No services, no queues, no database — the brief explicitly discourages building scaling infrastructure prematurely, and a single process is sufficient to demonstrate the abstractions.

Four seams, each a plain function boundary rather than a network boundary:

- **Perceive** (`surface/perceive.ts`) — turns the live page into a role/accessible-name element list plus a screenshot. DOM/accessibility-tree based, not screenshot-coordinate based, because that's what survives a surface with no clean DOM and no test IDs (the brief's stated common case).
- **Decide** (`discover/agentLoop.ts`) — an observe→decide→act loop against the Anthropic API using tool-calling, bounded to `MAX_STEPS`, with a closed action vocabulary (click/type/select/navigate/extract/wait) mirrored 1:1 with the artifact schema's action union. Two loop-control tools (`done`, `stuck`) never appear in a replayed artifact.
- **Act** (`surface/act.ts`, `surface/locate.ts`) — executes one action against a resolved `LocatorSpec`. This module is shared, unmodified, between discovery and replay: whatever locates an element during discovery is exactly what locates it during replay, so "recorded flow" and "replayed flow" can never silently diverge.
- **Record → Replay** (`discover/artifactBuilder.ts` → `replay/engine.ts`) — discovery's transcript is a narrower, structured shape (`discover/transcript.ts`), not the raw LLM chat history; the artifact is built only from that transcript. This is what makes the artifact "decoupled from the raw model transcript" per 3.2, and what makes replay a deterministic function of `(artifact, params)` with the model nowhere in its call graph.

Trade-off taken deliberately: locators are expressed in a small closed vocabulary (`role`, `label`, `text`, `css`) rather than an open-ended selector DSL. That bounds what replay has to be able to execute (simpler, auditable engine) at the cost of expressiveness — a genuinely dynamic layout might need something richer. Given the brief's "stable UI, real runtime errors" framing, this was the right trade.

## 2. Artifact schema

`artifact/schema.ts` (Zod, versioned via `schemaVersion`). Fields, and why:

- **`steps[]`** — ordered actions. Each `LocatorSpec` carries `primary` + `fallbacks[]` + a **`reasoning` string** — the brief asks explicitly for "how each target element is identified, with your reasoning about robustness," so reasoning is a first-class schema field, not a comment. A human reviewer or a calling agent can read *why* a locator was trusted, not just what it is.
- **`parameters[]` / `outputs[]`** — typed, named, described inputs/outputs, so the artifact reads as a callable function signature, not just a recorded macro. This is what makes it "an agent-invocable capability" per 3.2, not merely a step list.
- **`knownOutcomes[]`** — the artifact's declared error taxonomy: `code`, `category` (`business` / `recoverable` / `hard_failure`), a `detection` checkpoint, and for recoverable outcomes a bounded `recovery` action. This is the single most important field in the schema — see §3.
- **`successCheckpoint`** — an explicit assertion of the goal state, not an assumption that the last action worked.
- **`policy.riskLevel` / `requiresApprovalToReplayUnattended`** — the artifact declares its own risk; replay enforces it (§6).
- **`discoveredFrom`** — provenance (run id, model, timestamp), kept as metadata *about* the artifact rather than embedded in its executable content — so an artifact can be re-versioned or hand-reviewed without dragging transcript baggage through the replay path.

Design choice: locators for **data cells** (table cells whose text is the value being read, e.g. a balance) cannot use their own visible text as an identity — that value is different for every record. `artifactBuilder.ts#locatorFromElement` special-cases this: it anchors on the row's stable label cell (e.g. `"Savings"`) plus column position instead. This was found by actually running discovery and replaying against a second record (see §3) — the first version of the schema/builder didn't distinguish "clickable control identity" from "data cell content," and it's a distinction worth keeping explicit in the schema's mental model even though it isn't its own field.

## 3. Determinism & error handling

Replay is a pure function of `(artifact, params)`: no model call anywhere in `replay/engine.ts`. Determinism comes from three things, not one:

1. **Stable locators** — role/accessible-name first, text and structural CSS as fallbacks, tried in order (`surface/locate.ts`). Resolved identically whether the caller is discovery or replay (§1).
2. **Canonicalized checkpoints** — the success checkpoint's URL pattern is built by finding each declared parameter's *discovered literal value* in the recorded path and replacing it with a wildcard before regex-escaping the rest (`artifactBuilder.ts#canonicalizeSuccessPath`). Without this, an artifact discovered against member `12345` would report a hard failure for every other member, despite executing every step correctly — this was a real bug, caught by actually replaying against member `30500` and finding a false failure, not a hypothetical one.
3. **A closed, three-way result contract** (`replay/result.ts`): `success` (with outputs) / `business_outcome` (code + description — e.g. `MEMBER_NOT_FOUND`, "no such member" is a legitimate answer the caller needs) / `hard_failure` (step, expected, observed, screenshot). The glossary calls conflating outcome-vs-failure "the most common design mistake here"; keeping them as distinct discriminated result shapes (not a boolean plus a message) makes conflating them a type error, not a discipline problem.

Runtime conditions are handled by the artifact's own `knownOutcomes[]`, checked in order whenever a step's checkpoint fails or an action throws (`replay/engine.ts#handleFailure`): a `business` match returns immediately with the declared code; a `recoverable` match with a supplied handler (currently `reauthenticate`, for session expiry) retries the *same step*, bounded to `MAX_RETRIES_PER_STEP = 2` — never open-ended; anything unmatched becomes a `hard_failure`, screenshotted, and offered to `onStuck` (§5) before finally surfacing. Native `confirm()` dialogs are auto-accepted and logged rather than left to hang the run, since a bank UI's confirmation dialogs are a "recognized normal event," not a crash.

This was tested against real failures, not synthetic ones: `evidence/` includes a genuine `MEMBER_NOT_FOUND` and `PERMISSION_DENIED` business outcome, and a genuine hard failure (an unresolvable locator on an intentionally empty search result) that escalated to a human and was abandoned — see §5.

Secondary: UI drift. Because this environment is explicitly "stable UI, real runtime errors" rather than fast-moving, the design leans toward the fallback chain (locator degrades gracefully across small markup changes) rather than active drift *detection*. A confidence/staleness signal per artifact (replay N times, track fallback usage) is a natural next step, noted in §7.

## 4. Heterogeneity & multi-tenant

**Surface abstraction.** The seam between "how we perceive/act on a surface" and "the recorded flow" is exactly `surface/{perceive,locate,act}.ts` versus `artifact/schema.ts` + `replay/engine.ts`. The schema and replay engine know nothing about DOM, Playwright, or the browser — a `LocatorSpec` is `{by, role|label|text|css, reasoning}`, an action is `{click, type, select, navigate, extract, waitFor}`. To extend to a **legacy web app** with framesets/nested tables, `perceive.ts`'s element enumeration needs to walk frames and treat non-semantic markup with looser heuristics (already partly true: this project's own target has no test IDs and a table layout), but the schema doesn't change. To extend to a **desktop app**, `by` grows a `desktopAutomationId` / accessibility-API variant, `act.ts` gets an OS-automation implementation (e.g. via the platform accessibility API) instead of Playwright, and `target.surface` (already an enum: `web | legacy-web | desktop`) selects which perceive/act implementation replay loads — the artifact's steps, parameters, outputs, and known-outcomes stay the same *shape* regardless of surface. The generalization risk here is the closed locator vocabulary (§1): a desktop surface may need a genuinely different `by` variant, but the pattern (primary + fallbacks + reasoning) still holds.

**Multi-tenant reuse.** `artifact/appProfiles.ts` keys the known-outcome taxonomy by **`appId`** (a logical vendor-product identity, e.g. `meridian-teller-console`), not by tenant. The intent: an artifact discovered once against a base tenant carries `target.appId`; every tenant running that same vendor product shares the same `appId` profile (error taxonomy, allowlist route shapes) without a re-record. A tenant-specific override layers *on top of* the shared profile (branding differences, an extra required field, a moved button) rather than replacing it — not built here (the brief scopes multi-tenant as design-only), but the seam is the `appId`-keyed profile plus a per-tenant override map keyed by `(appId, tenantId)`, merged at replay time. **Drift detection**: the natural signal is *which locator fallback resolved* on a given replay (`ResolvedLocator.usedStrategy` / `usedFallbackIndex`, already returned by `resolveLocator` but not yet aggregated) — a tenant whose replays increasingly fall through to the CSS fallback is drifting from the base recording and is a candidate for review or re-specialization, without needing to re-record from scratch. **Canonicalization** (`/members/12345` → a parameterized pattern) is already partially built: `canonicalizeSuccessPath` generalizes the success-checkpoint URL by substituting declared parameter values; extending the same substitution to `navigate` action URLs is the natural next step for full route canonicalization (noted in §7).

## 5. Escalation & handoff

**Detecting stuck** happens in two places with the same shape: during discovery, the model can call a `stuck` tool when it can't tell how to proceed safely; during replay, any `hard_failure` not resolved by the known-outcome taxonomy is offered to an `onStuck` callback before being returned as a terminal failure (`replay/engine.ts#handleFailure`).

**Control-transfer model.** The browser is launched **headed** (a real, visible OS window), not headless — deliberately, so "taking control of the live session" is not a metaphor: the operator uses the *same window*, same cookies, same DOM state, with their own mouse and keyboard. There is no second session to spin up and no state to transfer over a network — automation's entire side of the handoff is "stop issuing Playwright commands against `page`, and don't resume until told to." That single rule is what makes the pause/resume boundary real. `escalation/intervention.ts` implements it: capture a before-screenshot and full context (`runId`, `capability`, `currentStep`, `reason`, `url`), log an `intervention_requested` event, block on a terminal prompt (`resume` / `abandon`), capture an after-screenshot, log `intervention_resolved`. The caller (`replay/engine.ts` or `discover/agentLoop.ts`) resumes the same step on `"resumed"`, or returns a terminal result on `"abandon"`.

**What's real vs. mocked**, per the brief's explicit scope note (3.6: "a full co-browsing operator console is out of scope"): the *mechanism* — pause, live session exposed for manual control, resume signal, evidence captured across the boundary — is real and demonstrated (`evidence/replay-*` includes a genuine forced hard failure that escalated and was abandoned, with before/after screenshots and the full event log). The *operator surface* is a terminal prompt plus the already-visible browser window, standing in for a real operator console; `cli/operator.ts` is a read-only view over the evidence trail (which runs have open/resolved intervention requests), not a live co-browsing UI. What's not captured: a step-by-step diff of the operator's individual clicks during manual control — that needs real operator-side instrumentation (event recording in the browser), which this project mocks rather than builds (§7).

## 6. Safety

Two independent, code-enforced mechanisms, applied identically in discovery and replay (not just documented):

- **Allowlist** (`safety/allowlist.ts`) — explicit `allowedOrigins`, `allowedRoutePatterns`, `allowedActionTypes`. `assertUrlAllowed` is called on every `navigate` during discovery *before* the browser follows it, and post-navigation on the resulting URL; a violation throws `AllowlistViolation` rather than proceeding. This is a refuse-before-acting model, not a log-after-the-fact one.
- **Risk classification** — `irreversibleRoutePatterns` marks specific routes (opening a sub-account) as irreversible; an artifact whose discovery touched one gets `policy.riskLevel = "irreversible"` and `requiresApprovalToReplayUnattended = true` automatically (`artifactBuilder.ts`). Replay enforces this as a hard gate (`replay/engine.ts`, `policy_gate` check) *before* executing a single step, unless the caller explicitly passes `approvedForUnattendedReplay: true` — demonstrated in `evidence/` (blocked, then approved). This is the "handle the risky class conservatively" requirement (3.4): block by default, require explicit approval, rather than a runtime confirmation prompt (which would defeat "no model/human in the replay loop" for the common safe case).
- **Redaction** (`safety/redact.ts`) — applied at the point of writing to disk, not left to callers: password/secret/token-named fields are replaced wholesale; any string field is scanned for 6+ digit runs (account/member/card-number shaped) and masked to the last 4 digits. `log/logger.ts` applies this to every field of every log event unconditionally.

**Limits, honestly**: the allowlist is a static, hand-authored config, not learned or audited automatically; redaction is pattern-based (field-name + digit-run heuristics), not a general PII classifier, and could both over-redact (a non-sensitive 6-digit number) and under-redact (sensitive text that isn't digit-shaped, e.g. a name). This is a deliberate scope choice for a project of this size, not an oversight — see §7.

## Stretch goals implemented

Two, picked for depth over breadth (per the brief's "at most one or two"):

- **Agent-facing capability interface** (`capability/{catalog,invoke,toolSchema}.ts`, `cli/capabilities.ts`) — saved artifacts are addressable as a named catalog, not just file paths. `--list` projects each artifact's own `parameters`/`outputs`/`description` into a tool definition in the same shape used for the discovery agent's own tool-calling (`llm/tools.ts`) — the projection can never drift from what replay actually accepts, since it's read straight off the artifact, not hand-maintained separately. `--invoke <name>` is a thin, typed front door onto the same replay engine, safety gating, and evidence logging `cli/replay.ts` already uses. This is the most direct demonstration of the brief's own framing: "the artifact becomes a reusable capability that the AI agents can invoke on demand."
- **Multi-run stability** (`replay/stability.ts`, `cli/stability.ts`) — replays an artifact N times and reports outcome distribution plus, per step, how often each one resolved via its primary locator vs. a fallback. This reuses data `resolveLocator` (`surface/locate.ts`) already computed but every call site previously discarded; `surface/act.ts` now logs it as a `locator_resolved` evidence event on every run (discovery included), which the stability check aggregates across N fresh replay runs. Real result against this repo's own artifact: 5/5 successful runs, 7/7 steps resolved via primary locator on every run — a measured signal, not a design claim. This is also exactly the signal §4 names as the way to detect per-tenant drift without re-recording.

## 7. Cuts

- **A real operator console.** Explicitly out of scope per the brief; a terminal prompt + the live browser window stands in. Real next step: a small web UI that can view the live page (via CDP screencasting or a shared VNC-like view) and record the operator's actual clicks as evidence, not just before/after screenshots.
- **The `open_member_sub_account` artifact was not discovery-recorded.** It's a hand-authored fixture (`discoveredFrom.runId: "fixture-hand-authored-for-engine-validation"`), used to exercise the replay engine's handling of a multi-field form, a `VALIDATION_ERROR` business outcome, and the irreversible-action approval gate — all verified working (see `evidence/` and the README demo). Only one genuine discovery run was required by the brief and delivered (`lookup_member_savings_balance`, including real bugs found and fixed by actually running it — see below); given more time, the sub-account flow would also be discovery-recorded to remove the one artifact in the repo that isn't provably model-generated.
- **Drift detection is now measured, but not yet gated on.** The "Multi-run stability" stretch goal (above) aggregates fallback-vs-primary locator usage across N replays, but nothing currently *acts* on that signal — no artifact is auto-flagged or blocked from unattended replay based on it. Wiring the stability signal into `policy.requiresApprovalToReplayUnattended` (the "Confidence & approval" stretch goal, not attempted) is the natural next step and would directly serve the multi-tenant drift story in §4.
- **Route canonicalization** is implemented for the success checkpoint only, not for `navigate` action URLs in general — a small extension of the same `canonicalizeSuccessPath` substitution.
- **No automated tests.** Correctness here was validated by actually running the system end-to-end multiple times (discovery + replay across several members and error cases) rather than by a unit-test suite, which is a real gap for a codebase meant to be maintained past a single session; `replay/engine.ts`'s outcome-matching logic and `locate.ts`'s fallback chain are the two places most worth covering first.
- **General PII classification.** Redaction is pattern-based, not a trained/general classifier — noted as a limit in §6, not fixed.

**Why "found real bugs" matters here**: the brief is explicit that "the discovery run has to be real... we can't assess a description of it." Actually running discovery end-to-end surfaced three genuine bugs that a description-only submission would never have caught: a tooling crash inside the perception layer, an unhandled multi-tool-call response from the model, and — most importantly — two correctness bugs where the artifact-building step baked a *discovered literal value* (a cell's own text, a URL's path segment) into what was supposed to be a generalized, reusable locator/checkpoint. All three are fixed and re-verified by replaying the corrected artifact against three different member records with three different real balances, plus the not-found, permission-denied, and forced-escalation cases.
